# irori 冷蔵庫・献立・買い物の連動監査 / 実装契約

2026-11-21。対象は `syouya0618/irori` の main `d13b505c` から作った独立ブランチ。現行の補充・買い物台帳を使い、DB migration / 認証設定 / 課金設定の変更は行わない。

## 正本とデータの流れ

| 現場での行動 | データの正本 | アプリの接続契約 |
|---|---|---|
| 食材・残量・賞味期限の登録 | `pantry_items` | 名前はカタログの辞書IDに厳密照合。数量不明や総称を「十分ある」と数えない |
| 料理の提案・手入力編集 | `dinner_plan_entries`、`dinner_plan_state` | レシピID+version、または手入力名+材料JSON。変更は枠の `updated_at` を要求 |
| 献立確定 | `confirm_dinner_entries` RPC | 提案から確定へ。家族が先に変更した版では拒否。使わない食材の判定が未確認なら保留 |
| 買うべき食材 | `grocery_items` の origin=auto | `buildGroceryNeeds` が確定献立の材料を人数・在庫・既使用予約で集約、`sync_grocery_auto_items` で反映 |
| 購入済みチェック | `grocery_items` の購入記録 | **購入チェックだけでは冷蔵庫は増えない** |
| 持ち帰った物の在庫追加 | `restock_pantry_from_grocery` RPC と `pantry_items` | 実際に確認した量を明示。restockの行IDを固定し再送で二重追加しない |
| 「作った」記録 | `dinner_plan_entries.status=cooked`、買い物の消費充当台帳 | いつ・何を作ったか。**物理在庫を勝手に減らさない** |
| 調理に実際に使った量 | `save_pantry_item` RPC | 本人が使用量を入力、単位と数量を検証、画面で反映後の残量を表示。押した1食材だけ、元の版で絶対残量を保存 |
| 家族の同期 | 同一householdのDB/RPC + 更新時再取得 | 即時同期ではなく、画面復帰/明示更新/定期pollで読み直す。版違いは上書きせず競合 |
| 調理の記録取消 | `restore_dinner_entry` RPC | 買い物の購入充当を戻す。実際に使った食材の物理残量は戻さない |

**混同してはならぬ2種類の減算**

- 買い物の `consumed_quantity` は「買った量のうち料理へ充当された量」という記録。
- 冷蔵庫の `pantry_items.quantity` は家に残る実数量。調理後に人が確認して更新する。
- 同じ食材を二重に減らさぬため、どちらも独立の事実として保つ。自動推定から実在庫は変更しない。

## 監査で発見した不足と解消

1. 既存の1品手入力変更はレシピの材料欄が空で始まり、名前だけ変更すると買い物自動計算から脱落した。
   - レシピの元の材料を、登録された人数に `scaleQuantity` でスケールし、任意材料フラグを含めて編集フォームへ初期表示する。確定する前に利用者が変更/削除できる。
   - 手入力へ変更した後の材料は料理の登録人数に対応する**絶対量**として保存する。再度スケールしない。
2. 既存の調理後フォームは「ある/残り少ない/使い切った」だけで、実使用量からの残量計算UIがなかった。
   - `deductPantryUse` は負数・在庫超過・単位不一致・数量不明を拒否する純粋関数。
   - 例えば2束から1.5束使えば残0.5束。1kgから250gなら0.75kg。ゼロなら`quantity=null,status=out`。
   - 元の単位を保持し、正しい使用量を押すまで保存しない。複数食材は**1食材ずつ**確定し、途中で部分更新したときの取り違えを防ぐ。
   - 保存APIは既存 `applyCookedPantryUpdates` → `save_pantry_item`。押下時の固定された絶対残量と旧版で送るため、通信再送でも再計算して二重減算しない。
3. 画面遷移を省略する新しいDBテーブルや、レシピの目安から強制的に在庫を減らす自動化は**実装しない**。実使用の事実が分からないため。

## 整合性・安全ゲート

- 家族・プロフィールは毎回 `getAuthContext`、書込は世帯に閉じたRPC経由。サービスロールはブラウザへ渡さない。
- ユーザーは使用量だけ入力する。クライアントの計算を経た**絶対残量**を既存の更新版でCAS保存する。他端末が既に編集していたら以前の版で上書きしない。
- 数量が不明/期限を過ぎているときは「作れる」と断言しない。使用量を推定して差し引かない。
- 食材の任意材料は、手入力に変換しても任意のまま。買い物へ必須材料として足し直さない。
- 一連のUIと2アカウントの競合は、localhostの使い捨てSupabaseのみでPlaywright検証。Previewは本番DBへつながるため、合成データの書込み先にしない。
- 現在のPR #265（棚卸し重複・総称の具体化）は別の作業中ブランチ。無断で混合・変更・マージしない。

## 残る設計上の限界

物理在庫の使用履歴を「献立の調理記録」と不可分のトランザクションで保存する専用台帳は存在しない。そのため`作った`を取り消しても、実際に差し引いた在庫を自動で戻さない。戻す場合は在庫画面で別途修正する。これは誤った自動復元を防ぐ意図した境界。

もし将来、誰が何g使ったかの監査台帳、期限別ロットのFIFO、複数食材の一括原子更新、二端末間の即時Push同期が必要なら、**独立したDB migrationとRPC設計、およびProduction変更の個別承認**が必要。
