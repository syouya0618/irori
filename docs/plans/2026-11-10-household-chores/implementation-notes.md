# 家事（ごみ・掃除・ごはん）実装メモ

要件は `requirements-ledger.md`、進捗と証拠は `progress.md`。ここは設計判断だけを置く。

## 0. 共通方針

- route: `/chores`（家事ハブ）, `/chores/garbage`, `/chores/cleaning`, `/chores/meals`（配下に `now` / `plan` / `shopping` / `pantry` / `settings` / `recipes/[id]`）。すべて `src/app/(main)/` 配下に置き、既存の 3 層ゲート（proxy → layout → 各 Action の `getAuthContext()`）をそのまま使う。viewer（子ども閲覧招待）は layout で `/shared` へ送られる。
- ナビ: BottomNav を 4 タブ（育児 / 予定 / 家事 / 設定）にする。5 タブ目は足さない（320px で帯がはみ出す）。起動時ページ（`VALID_PAGES`）と SW の `APP_PAGES` には初版では足さない（DB CHECK と SW バイト列を動かさない）。
- 権限: 新規テーブルは全て世帯単位。`ENABLE RLS` → `REVOKE ALL ... FROM PUBLIC, anon, authenticated` → authenticated へ `SELECT` のみ → `GRANT ALL TO service_role`。SELECT ポリシーは `TO authenticated USING (irori_private.is_household_editor(household_id))`。書込は `SECURITY DEFINER SET search_path=''` の RPC だけ（世帯 ID は引数で受けず `auth.uid()` から導出、`REVOKE ALL ... FROM PUBLIC, anon, authenticated` → `GRANT EXECUTE TO authenticated`）。直接 DML の GRANT が無いので INSERT/UPDATE/DELETE ポリシーは作らない（= 拒否）。`child_shares` を述語に登場させず、`shared_child_snapshot` に触れない。
- 保存契約: 第 2 世代（RPC が `saved / replayed / conflict` を返す）。行 ID はクライアント採番 UUID、版は `updated_at`（PostgREST の表記のまま運ぶ）。端末の控えは世帯スコープの `chore-pending`（`src/lib/domain/chore-pending.ts`）を 3 機能で共有し、`CacheUserGuard` と `local-work.ts` へ配線する。自動再送はしない。
- 他端末への反映: Realtime publication には足さない（2026-10-30 以降の新規表と同じ）。`useVisibilityRefetch(router.refresh, pollMs)` で「画面へ戻ったとき」と「表示中の定期再取得」で回収し、買い物・献立の画面に反映タイミングを文言で示す。
- 旧テーブル名（`meals` `meal_templates` `meal_ingredients` `meal_reactions` `shopping_items` `stock_items` `purchase_history` `eating_out_logs`）と旧 ENUM 名は再利用しない。`20260909100003`（DROP）が本番適用済みかは repo から判定できないため、別名で衝突を避ける。ENUM は作らず `text + CHECK`。
- migration（この順で適用。全て加算のみ）:
  1. `20261111100001_event_purposes.sql`（ごみ分類）
  2. `20261111100002_cleaning_routines.sql`（掃除）
  3. `20261111100003_dinner_tables.sql`（ごはん）
- 日付: `src/lib/utils/date-jst.ts` と `src/lib/domain/ymd-math.ts`（月加算の月末寄せ・閏日）だけを使う。SQL 側の「今日」は `(now() AT TIME ZONE 'Asia/Tokyo')::date`。

## A. ごみ

### データ

`public.event_purposes`: `(household_id, scope, target_key)` を CONSTRAINT で UNIQUE。calendar_events への FK は張らない（Google の 410 完全再同期は行を DELETE→INSERT し行 ID が変わる。`event_uid` は不変）。

| scope | target_key | 意味 |
|---|---|---|
| `series` | native: `series_id::text` / google: `google_calendar_id \|\| '\|' \|\| recurring_event_id` | シリーズ既定 |
| `event` | `event_uid` | 単発の分類、またはシリーズ内の単回例外 |

- `scope` を鍵に含める理由: native の `series_id` は初回行の `id`（= `event_uid`）と同値になり得る。
- 列: `purpose`（`garbage` / `normal` / NULL）、`garbage_kind`（1〜20 文字の名称）、`remind_default`（`prev_day_20` / `none`。series のみ意味を持つ）、`reminder_opt_out`（event のみ。この回の通知を明示的に止めた印）。`target_key` に長さ上限を付けない。
- 解決順: event 行の `purpose` が非 NULL ならそれ → series 行 → 未分類。event 行の `purpose='normal'` が「この回だけ通常予定へ戻す」例外。
- 書込は RPC `save_event_purpose(p_event_id, p_scope, p_action, p_garbage_kind, p_reminder, p_seen_series, p_seen_event)`。クライアントは行 ID だけを渡し、鍵（`event_uid` / シリーズキー）はサーバーが `calendar_events` から引く（`CALENDAR_EVENT_COLUMNS` に新設列を足さない）。`medical_record_id` 付きの予定は対象外。
- `p_seen_series` / `p_seen_event` は、フォームを開いた時点の分類行の版（`updated_at`。行が無ければ NULL）。今の版と違い、適用すると何かが変わるときは何も書かず `conflict` を返す（結果不明の控えを後から再送しても、家族の新しい分類と通知を消さない）。求める状態が既に成り立っていれば `replayed`。
- 予定を利用者が削除した後の掃除は RPC `cleanup_deleted_event_purposes`（native の鍵だけ。予定が残る行は消さない）。

### 通知（既存 `event_reminders` へ接続。新 cron・新 kind なし）

- 「未設定」と「明示 OFF」は `event_reminders` では区別できない（OFF = 行 DELETE）。真値はドメイン表に持つ: series の `remind_default` と event の `reminder_opt_out`。
- 分類フォームは今回保存する通知設定を明示する。`p_reminder`:
  - `prev_day_20`: 未設定の回へ前日 20:00 を追加（`ON CONFLICT DO NOTHING`。設定済みの時刻は変えない）。series なら `remind_default='prev_day_20'` にし、今日以降の全回へ適用（`reminder_opt_out` の回と通常へ戻した回は除く）。
  - `off`: event はその回の reminder を消して `reminder_opt_out=true`。series は `remind_default='none'` にして今日以降の回の reminder を消す（利用者の明示操作として UI に範囲を書く）。
  - `keep`: 通知設定に触れない。
- 将来回: `calendar_events` の AFTER INSERT トリガが、series 既定が `prev_day_20` で opt-out されていない今日以降の回に reminder を足す（Google 同期で後から届く回・410 後の再挿入を含む）。`event_reminders` の AFTER DELETE トリガは、既定 ON のシリーズの回が個別に OFF されたとき `reminder_opt_out` を立て、AFTER INSERT は解除する。これで 410 再挿入が明示 OFF を上書きしない。
- 「シリーズ全体を止めた」と「この回だけ止めた」は別々に記録する。予定シートの通知欄から 1 文で同じシリーズの今日以降の通知が 2 件以上消えたらシリーズ全体の停止（`remind_default='none'`）、1 件だけなら回ごとの `reminder_opt_out`。ごみ画面でシリーズを前日通知へ戻すと、個別に止めた回は戻さず、それ以外の回へ通知を付け直す。既知の制限: 今日以降に通知の付いた回が 1 つしか無いシリーズを予定シートで「なし」にすると個別停止として記録される（勝手に戻さない側）。
- 過ぎた日から今日以降へ日付を動かした回にも既定の前日通知を足す（トリガは `AFTER INSERT OR UPDATE OF start_date`）。前日 20:00 を過ぎた回には画面で「通知します」と言わず、届かないことを伝える。
- 二重送信防止は既存のまま: `uq_event_reminders_event (household_id, event_uid)` と `uq_notification_deliveries`。日時変更・削除・OFF 後の再確認も既存の `processPending` が担う。通知の遷移先は既存の `/calendar?date=`。
- 整理条件: 分類行を消すのは (a) 利用者の解除、(b) 利用者による予定・シリーズの削除（Action 内の best-effort 掃除）だけ。同期の 410 経路・配信経路では消さない。予定が見つからない分類は「予定が見つかりません（同期中の可能性があります）」としてごみページに出し、手動で整理できる。

### 表示

- 予定の取得 4 箇所（カレンダー SSR / client refetch、育児ホーム SSR / client refetch）で、既存列だけを足した別定数（`event_uid, google_calendar_id, recurring_event_id`）と `event_purposes` の世帯一括 SELECT を並べ、純関数 `resolveEventPurpose` で合成する。分類の取得に失敗しても予定表示は倒さず、分類を「不明」として扱う（未分類と偽らない）。
- 月セルと選択日一覧は Lucide アイコン＋名称で区別し、色は補助。aria-label に「ごみ（名称）」を含める。

## B. 掃除

### データ

- `cleaning_routines`: `name`, `location`, `cadence_unit`（week/month/year）, `cadence_interval`, `schedule_mode`（`fixed` / `after_done`）, `anchor_date`, `postponed_occurrence` + `postponed_until`, `paused_at`, `resume_floor`, `archived`。
- `cleaning_logs`: `kind`（done/skip）, `done_on`, `occurrence`（閉じる対象回の鍵。過去日の追記は NULL）, `scheduled_on`（skip だけが持つ、その回の予定日。延期前）, `voided_at`。
- `UNIQUE (routine_id, occurrence) WHERE occurrence IS NOT NULL AND voided_at IS NULL` で、同じ回の同時完了を 1 行に確定する。RPC は routine の版（`updated_at`）も受け、周期が変わっていたら `conflict` を返す。

### 周期の規則（純関数 `src/lib/domain/cleaning-schedule.ts`）

- fixed: 予定日は基準日から生成（週 = 7×n 日、月 = 基準日の「日」を保ち無い月は末日、年 = 基準の月日で 2/29 は平年 2/28）。毎回「元の基準日」から計算するので月末・閏日がずれ続けない。
  - 対象回 = 「今日以前で最も新しい未完了の予定日」（無ければ次の予定日）。完了はその回を閉じ、次回は「閉じた回より後で今日より後の最初の予定日」。途中で逃した回は実施済みにしない。期限超過日数は「最も古い未完了の予定日」から数える。
  - 過去日の追記（`occurrence` NULL）は現在の回を閉じない。
- after_done: 予定日 = 最後の閉鎖（done なら `done_on`、skip ならその回の予定日）＋周期（月・年は暦で加算、月末寄せ）。履歴が無ければ基準日。実施基準なので、最新の実施日より新しい過去日を追記すると次回予定は再計算される。
- 延期: 現在の回の期限だけを `postponed_until` へ動かす（基準日・前回実施日は不変）。次の回には及ばない。
- スキップ: `kind='skip'` の履歴。fixed は次の予定日へ、after_done はその回の予定日から次周期へ。前回実施日は動かない。
- 休止・再開: 再開日を `resume_floor` に入れ、それより前の予定日は対象にしない。
- 未来日の実施記録は RPC が拒否する。前回実施日 = 有効な done 履歴の最大 `done_on`（無ければ「未記録」）。
- 周期の世代（`cadence_epoch`）: 周期（単位・間隔・方式・基準日）を変えると世代が 1 進み、回の一意性・閉じ済み判定は今の世代だけを見る（変更前の格子で閉じた鍵が新しい格子の予定を覆わない）。前回実施日は全世代から取る。名前だけの編集とアーカイブ復帰では進めない。
- after_done の起点は「最後の閉鎖」（日付の大きい方ではない）。スキップが最後の閉鎖なら、その回の**予定日**（鍵ではない）から数える（B-07f。下の追補）。
- B-07f 追補（2026-11-11。`20261111100002_cleaning_routines.sql` は本番未適用の新規 migration ゆえ、新しい migration を足さずその場で編集した）:
  - 不具合: after_done の鍵は予定日から逃げうる（早めに実施して次の予定日が閉じた鍵と重なると翌日へ。例: 基準日 11/11・履歴なし → 11/4 に実施して鍵 11/11 を閉じる → 次の予定日 11/11 は鍵 11/12）。スキップの履歴が鍵しか持たなかったため、スキップ後の次回が鍵から数えられて 1 日ずれた（11/18 のはずが 11/19）。予告（「スキップすると次回は…」）も鍵から数えていた。予定日は鍵からは復元できない。
  - 修正: `cleaning_logs.scheduled_on` を足した（CHECK: done は NULL、skip は NOT NULL かつ `scheduled_on <= occurrence`）。値は `record_cleaning_log` が世帯ロックの下で有効な履歴から計算して入れる（引数は増やしていない = 署名不変。RPC を直に呼ばれても同じ値）。計算した今の鍵が `p_occurrence` と一致しない時（今の回ではない鍵を直に閉じた）は鍵そのものを入れ、無関係な予定日を植えない。固定周期の鍵は格子の予定日そのもの。再送（同じ操作 ID）は既存行を返すだけで、予定日を計算し直さない。延期中の回のスキップも延期前の予定日を残す。
  - `cleaning_log_marks` に `last_skip_scheduled_on`（`max_skip_occurrence` の回の予定日）を足し、TS の `marksOfLogs` / `routineStatusFromMarks`（`lastSkipScheduledOn`）と `nextAfterSkip`（予定日 + 周期）を同じ規則に揃えた。予定日を持たぬ要約・行は鍵へ退化する（`src/lib/types/database.ts` も更新）。
  - 回帰: `src/lib/domain/__tests__/cleaning-schedule.test.ts`（B-07f。月末・閏日・延期・再開日・連続スキップ・固定の対照）と `supabase/tests/cleaning_routines.sql`（予定日の保存・再送・月末・閏日・守り・CHECK）。修正を「鍵を入れる」形へ戻すと、DB は 11/19 対 11/18 の食い違いで赤になる。
  - 残る制限: 今の回ではない鍵を RPC で直に閉じた skip は鍵そのものを予定日に持つ（その経路だけ 1 日のずれが残りうる。画面・Server Action は常に今の回を閉じる）。done の鍵が今の回かは DB で検証していない（従来どおり）。旧版のこの migration を適用済みのローカル・preview の DB には反映されぬゆえ、`supabase db reset` 等で作り直すこと。
- 1 タップ完了の実施日は最初の押下で固定する（`pressedOn`。画面が持つサーバー由来の今日が端末の日付と一致するときだけ。食い違えばサーバーが受けた日で記録し、成功の文で日付と直し方を伝える）。日を跨いだ再送でも同じ日付で記録する。
- 編集フォーム（項目・履歴の訂正）は開いた時点の版を固定して送る。背景で版が進んだら保存を止め、明示の操作で最新を読み込み直す（上書き保存は置かない）。
- 履歴は一覧（世帯の直近 300 件）から外れた分も、項目ごとに 20 件ずつ読み足して訂正・取り消しできる。

## 共通の追補（レビュー後）

- 他端末の変更の再取得は `router.refresh()` を直接呼ばず、`src/components/chores/shared/refresh-gate.ts` の門を通す。圏外では呼ばず、直近にサーバーへ届いた証拠が無ければ `GET /api/version` で先に確かめる（失敗時に画面と未保存入力が `/offline` へ置き換わらないため）。自動の再取得は、送信中・開いたシート・入力途中の欄がある間は見送る。
- 再取得の失敗では直前の内容と入力中の状態を保ち「最新の内容に更新できませんでした」を出す（`keep-last-good.tsx`）。初回の失敗は従来どおり error.tsx。「今あるもので」だけは古い提案を残さず失敗表示にする（新しい除外が効かない料理を出さないため）。
- 結果不明の控えは、通信できる状態での「同じ操作で確認」が 2 回結果不明に終わった後にだけ、2 段確認つきで取り下げられる（端末の控えだけを消す。操作は取り消されない旨と、やり直す前に画面で確かめる旨を警告）。
- R35（2026-11-11。掃除・ごみの画面とカレンダーのごみの欄）: 保存の応答は、その操作を送った編集セッションのシートにだけ効く。共通の `useChoreSave` に編集セッション（`createChoreEditSessions` の番号札。シートを開くたび・中身を切り替えるたびに増える番号で、レコード ID ではない）を足し、送信の時の番号と応答の時の番号を比べた結果を `outcome.origin`（`current` = 送ったシートが今も開いておる / `inPlace` = 操作した場所が今も同じ）に載せる。
  - 古い応答でも行う: その操作自身の控えの確定・結果不明への更新、一覧の取り直し、一覧の部品（掃除の直後の取り消しの帯）。
  - 送ったシートが今も開いておる時だけ: シートを閉じる・入力の初期化・触れた入力欄の記憶を捨てる（`clearUnsavedInput`）。送った後に閉じた・別のシート（同じ項目の開き直しも）を開いた時は、開いておるシートの入力・保存中の表示（送信中の控えの番号がそのシートの時だけ「保存中」）に触れない。
  - 結果の文言は操作した場所が同じ時だけそこに出す。違えば「先に送った操作（…）は保存できませんでした。…」のように、どの操作かを添えてシートの外（掃除・ごみは一覧、カレンダーは toast）に出す。
  - 「同じ操作で確認」はどのシートの送信でもない（応答でシートを閉じない。結果不明の後に打ち直した入力を、先の内容の確定で消さない）。文言は押した場所に出す。
  - 献立の画面は番号札を渡さず従来どおり（各画面が自前で R35 を直している）。番号は端末の控えに書かない。

## C. ごはん

### 構成

- カタログはコード同梱（`src/lib/meals/catalog/`）。DB seed は無い = 投入は常に冪等で、本番へテストデータを入れない。出所は Irori 独自作成のみ。
- 自動献立（規則ベースの純関数）が中核。生成 AI は「希望文の構造化」と「候補 ID の並べ替え」だけを補助し、無くても同じ画面が動く。画面は経路を区別して表示する（`自動` / `AI 補助`）。
- 計算はサーバー（Server Action / Server Component）で行い、カタログを育児トップの bundle へ載せない。

### 判定の規則

- 食材名の照合は「正規化後の完全一致（表示名・別名）」だけ。部分一致しない。解決できない在庫は名前のまま保持し、提案の材料に数えない。
- 在庫の充足は 3 段: `ready`（必須材料が全てあり、数量も足りる／常備品）・`check`（あるが数量不明・残り少ない・単位が換算できない・最終確認が古い）・`buy`（必須材料が欠ける）。期限超過と「使い切った」は欠品扱い。常備品は世帯が設定したものだけ。
- 必須除外は世帯の和集合。アレルゲンは食材辞書の構造化情報（派生食材を含む）で判定し、候補作成の前後 2 回検証する。`allergenInfo='varies'` の材料や `allergenStatus='unconfirmed'` のレシピは、アレルギーの除外が 1 つでもあれば自動確定の候補から外す（「原材料の確認が必要」として別枠）。自由入力の除外は辞書へ解決を試み、解決できなければ名前の一致で除外したうえで、判定の限界を画面に出す。
- 年齢制約（1 歳未満のはちみつ等）は食材辞書の `ageRule` に一次資料の出典つきで持つ。取り分け案内は `childServing` を持つレシピだけに表示し、未設定・対象外では「未対応」と表示する。
- 献立: 固定枠は全操作で保持（DB 側でも固定枠を上書きしない）。在庫は日付順に計画上で引き当て、実在庫は減らさない。計画全体は `dinner_plan_state.revision` で楽観排他し、AI 応答の採用時も版を再検証する。
- 買い物: 食材 ID と単位の族が同じものだけ合算（g↔kg、ml↔L↔小さじ・大さじ・カップ）。個数系・適量・少々は数値化しない。自動項目は `item_key` で upsert し、購入量・メモ・手動項目を保持する。残り = 必要量 − 購入量（300g 購入後に 500g へ増えたら 200g が未購入）。在庫への補充は別操作で、確認した量を一度だけ反映する。

### 購入の事実・作った料理への充当・取り消し（2026-11-11 の修正。migration `20261111100003` をその場で編集）

修正前は、同期（`sync_grocery_auto_items`）が「購入の消化」として、作った枠・確定のまま日が過ぎた枠の `buy` を `purchased_quantity` から直接引き、数値化しない項目は `purchased` を外していた（購入の事実を書き換える。取り消しても戻さない）。また `restoreDinnerEntry` は常に「確定」へ戻すため、提案のまま「作った」にした料理を取り消すと、元は買い物に無かった料理が買い物へ入った。これを次のとおり分けた。

- **4 つの事実を分ける**: 購入の事実（`purchased_quantity` / `purchased` / `purchased_at` / `purchased_by`）・献立への引当（出所 `sources` の `entryId` / `buy`）・在庫への補充（`restocked_quantity` / `restock_ids`）・実消費（新設の台帳）。購入の事実を書くのは `set_grocery_purchase` だけ。同期も「作った」も書き換えない。
- **実消費の台帳**（`grocery_items` の同じ行。行ロックが局所で済むため）:
  - `consumptions jsonb` = `[{k: 枠 ID | 'settled', q: 充当量, m: 印のまとまりか, d: 枠の日付}]`、`consumed_quantity` = q の合計。一致は CHECK `grocery_items_consumptions`（`irori_private.dinner_ledger_total`。形が違えば NULL → 拒否）で DB が守る。この関数は CHECK から呼ばれるため service_role にだけ EXECUTE を与える（authenticated / anon には与えない。RPC は所有者として書く）。
  - `purchase_consumed boolean` = 購入の印を作った料理で使い終えたか。画面の印 = `purchased AND NOT purchase_consumed`。CHECK `NOT purchase_consumed OR purchased`。
  - 書くのは同期の RPC だけ。行ごとに (1) 既存の記録を見直す → (2) 充てられる量を計算 → (3) 済んだ出所を記録、の順。
    - (1) 記録の枠が世帯に在り、もう消費済みでない（取り消し・作らなかった・未来へ移動）か、この項目の新しい必要量に再び載った → **その記録だけを外す**（= 当該の操作の差分だけを戻す）。枠が消えた（取り消せない）・35 日より前の枠は、充当を残したまま `settled` へ畳む。150 件を超えた分も古い順に畳む。
    - (3) 新しい必要量から外れ、作った（または確定のまま日が過ぎた）枠を、記録の無い枠に限り 1 回だけ記録。量 = min(出所の buy, その時点で充てられる購入)。同じ行で複数を記録するときは充てられる量を順に減らす。枠の無い出所は取り消せないので `settled` へ直接。献立の変更（削除・差し替え・作らなかった）で外れた分は記録しない。
    - 数値化しない項目: 印が生きている間に済んだ枠を、まとまり（`m=true`, `q=0`）として記録し、出所が全て済んだら `purchase_consumed=true`。まとまりの枠が 1 つでも未消費に戻れば印が戻る（同じ同期で 2 枠が済んだ後に 1 枠だけ取り消しても戻る）。量の項目は「充当を足したら立て、記録が外れたら下ろす」。

- **残りの式**（SQL のコメント・`grocery.ts` の `remainingToBuy` / `restockableAmount`・画面で同じ）: 今の必要に充てられる購入 = `purchased_quantity − restocked_quantity − consumed_quantity`（0 未満にしない）。不足 = `required_quantity −` それ。在庫へ足せる量も同じ式（作った料理に使った分を在庫へ足せない＝取り消しで在庫は増えない）。

  - 材料の正規化 ID・派生（`derivedFrom` / `refinedFrom`）・辞書のアレルゲンで判定する（料理名に「卵」が無くても、材料のマヨネーズで当たる）。手動料理は料理名も照らす。
  - **原材料が分からないものを「含まない」と判定しない**: 除外が 1 件でもある世帯では（苦手だけでも）、材料未登録の手動料理・辞書で解決できない材料・カタログに無いレシピは「未確認」（以前はアレルギーの世帯だけ）。商品で原材料が変わる材料（`varies`）・未確認のレシピは、従来どおりアレルギーの世帯だけ「未確認」。
  - **確定（`confirmDinnerPlan`）は「当たる」も「未確認」も止める**（以前は「当たる」だけ）。固定・手動の料理を含めて 1 品でも在れば何も確定しない。献立の画面も確定の釦を止め、料理名と理由を出す（`plan-confirm-held`）。手動料理の保存は止めず（下書き）、保存の結果を警告として返す（`exclusionWarning`）。**確定済みの料理を「当たる」「未確認」の内容へ直したとき（手動料理の編集）・作った／作らなかったの取り消しで確定へ戻すとき（その間に除外が増えた）は、確定のままにせず提案へ戻して知らせる**（レビュー[重 1]。確定は「問題なし」の料理だけ = 買い物に入るのも「問題なし」の料理だけ）。既知の限界: 除外を足した時点で既に確定している料理は、献立の画面・設定の重なりの一覧で衝突として出すが、状態は変えない。買い物の自動計算からは外し、理由を出す（2026-11-11。「購入の事実・作った料理への充当・取り消し」の節）。
  - **「含む」での照合の部分一致**（自由入力の推定 `resolveByContainment`・手動料理の料理名）: 品目名を含むが、その品目ではない語の中の名前を数えない（`exclusion-terms.ts` の `hides` / `DEFAULT_NAME_MASKS`）。決めた期待値: 焼きそば → 焼きそば麺（小麦）・そばではない / 豆乳 → 豆乳（大豆）・乳ではない / 鶏もも → 鶏もも肉（鶏肉）・もも（桃）ではない / さけるチーズ → チーズ（乳）・さけではない。4 つとも**食材（加工品・部位）止まり**で、アレルギーでもアレルゲン全体（小麦・大豆・鶏肉・乳）へは広げない（R23 の「加工品の登録から原因の成分を推測しない」にそろえた。「豆乳」アレルギーで豆腐・しょうゆの料理は外れない、「鶏もも」アレルギーで鶏むね肉の料理は外れない — 広げるかは辞書の `allergySpread` で一括に決める事柄として残す）。料理名の側も同じ（豆乳鍋 × 乳アレルギーは当てない・× 大豆アレルギーは当てる）。本当にその品目を含む語（ざるそば・ぽん酢 ⊃ 酢・塩鮭 ⊃ 塩）は隠さない — 隠す語の品目の由来・アレルゲンに隠す品目が無いことをカタログのテストが守る。
  - 解決できない自由入力（「からいもの」等）は「適用済み」に見せず（従来どおり「自動では判定できません」）、登録の前の確認に「対象品目から選び直す」「食材から選び直す」を出す。
  - 分類の語は、含む品目 1 つへ縮めない（レビュー[低 8]）: 「〜科」（なす科・うり科）は「含む」では解決せず「判定できない」に、「〜類」は類全体を指す品目（アレルゲン名「えび」・総称の食材「きのこ」）にだけ解決する（「なす類」は判定できない）。総称・類義の語の辞書（ナッツ類・魚介類…）と完全一致は従来どおり。設定画面の語彙にも総称の印（`generic`）を載せ、画面と判定を一致させた。
- **補充の上限は RPC が守る**（`restock_pantry_from_grocery`）: 以前は Server Action だけが「購入 − 補充済み − 作った料理への充当」を上限として守り、RPC を直に呼ぶと購入より多く補充できた。量で追う購入は、充てられる量（0 なら数量不明でも不可）を超えたら 22023、上限ちょうどは通す。量の無い購入（印だけ）は量の上限を持たない。買っていない項目は 22023。Action は RPC の拒否を利用者向けの文に直す。pgTAP `supabase/tests/dinner_tables.sql` §19。

### AI（追加課金 0 円）

- 経路は Cloudflare Workers AI の REST 直接呼出し 1 本のみ。AI Gateway・有料 fallback は実装しない。
- 有効条件は env（`MEAL_AI_ENABLED` / アカウント ID / token / モデル）。Workers Free であることは API から判定できないため、人がダッシュボードで確認してから有効化する（確認できるまで `blocked`）。
- 世帯 1 日 10 操作、1 操作の retry は最大 1 回で retry も計上。内部コード 3036（日次無料枠の枯渇）は次の 00:00 UTC（09:00 JST）まで全世帯の呼出しを止め、3040（一時的な容量不足）とは区別する。どちらの場合も自動献立は続く。
- 送るのは希望文（長さ上限つき・データとして扱う）、対象日の一覧、必須除外を適用済みの候補（ID・料理名・タグ）だけ。氏名・生年月日・育児記録・診断名・アレルギーの内容は送らない。返ってきた ID は候補集合と日付範囲で検証し、外れたものは捨てる。
